# 아키텍처

`docs/PROMPT.md`의 명세를 구현하기 위한 설계 문서다. 명세가 바뀌면 이 문서도 같이 고친다.

## 1. 요구사항 요약

- 사용자가 고른 음악 파일과 키 모드·난이도로 **채보를 자동 생성**하고, 그 채보를 플레이하는 건반형 리듬게임.
- **곡 분석·채보 생성·난이도 산정은 로컬 Python 서버**가 맡는다. 브라우저 클라이언트는 플레이만 한다.
- **판정 범위는 DJMAX RESPECT V 기준**(NORMAL / HARD / MAX JUDGEMENT).
- **플레이 화면은 SOUND VOLTEX식 3D 원근 트랙**: 판정선 쪽 낮은 시점에서 트랙이 화면 위쪽 소실점으로 뻗어 나간다.
- 품질 우선순위: 싱크·판정 정확성 > 음악과 맞는 채보 > 믿을 수 있는 난이도 > 손맛.

## 3. 전체 구조

```
┌──────────── 브라우저 클라이언트 (TypeScript) ────────────┐        ┌────────── 로컬 Python 서버 (FastAPI) ───────────┐
│ ui/       곡 선택 · 설정 · 결과 · HUD · 배경(BGA)        │  HTTP  │ api/        라우트, 라이브러리(SQLite+파일)     │
│ editor/   채보 에디터 (편집 규칙 · 캔버스)               │◀──────▶│ audio_io    디코딩 → 표준 FLAC, 태그·커버       │
│ render/   Three.js SDVX식 트랙 · 카메라 연출 · 스킨      │        │ analysis/   기본 분석 · 스템 분리 · 악기 태깅   │
│ engine/   판정 · 점수 · 게이지 · 오토 플레이 · 리플레이  │        │   backends/ ML 어댑터 (Demucs · beat_this 등)   │
│ input/    키보드·게임패드 → 레인, 타임스탬프 변환        │        │ generator/  채보 생성 · 린터 · 연출 신호        │
│ audio/    표준 오디오 재생, 오디오 클럭, 키음            │        │ difficulty/ 레벨 산정                           │
│ settings/ 설정 · 키·패드 배치 (localStorage)             │        │ formats/    osu!·BMS·bmson 가져오기/내보내기    │
└──────────────────────────────────────────────────────────┘        └─────────────────────────────────────────────────┘
              config/ (판정 · 키 모드 · 게이지 · 카메라 · 난이도 · 분석 · 악기 · 입력) 공용
              desktop/ Electron 창 + PyInstaller로 묶은 서버 (선택)
```

- 업로드 → 서버가 표준 FLAC 생성 → 분석(백그라운드 작업, 진행률) → `AnalysisResult` 캐시.
- 채보 요청(키 모드, 난이도, 시드) → 생성기 ⇄ 난이도 산정 루프 → `Chart` JSON 캐시 → 클라이언트. 선곡은 커서가 300ms 머문 곡의 고른 난이도는 채보 전체를, 다른 난이도는 `brief`(메타만, 디스크에 저장하지 않음)로 받아 모든 레벨을 바로 보인다. 같은 요청은 한 번만 하고, 요약 4000개와 채보 8개를 화면을 오가도 기억한다(`ui/chartCache.ts`). 생성 채보의 요약은 최근 2000개를 서버 health의 생성기 버전과 함께 localStorage `grg.briefs.v1`에 남겨, 다시 켜도 곡 목록에 레벨이 바로 나온다. 생성기 버전이 바뀌면 같은 옵션도 다른 채보가 되므로 남긴 요약을 버린다. 다른 곡을 미리 받아 두지는 않는다.
- 클라이언트는 표준 FLAC을 받아 `decodeAudioData`로 디코딩해 재생한다. 채보의 `t`는 이 PCM의 첫 샘플이 0ms다.

## 4. 시간 모델

리듬게임에서 가장 중요한 부분이라 규칙을 명시한다.

- **곡 시간(song time)**: 표준 오디오의 재생 위치(ms). 스피커에서 *지금 들리는* 샘플 기준이다.
- **오디오 클럭이 유일한 기준**이다. `AudioContext.getOutputTimestamp()`가 주는 `(contextTime, performanceTime)` 쌍으로 `performance.now()` 시간축을 오디오 출력 시간으로 매핑한다. 쌍이 갱신될 때마다 오프셋을 지수 평균으로 다듬어 지터를 없애고, 50ms 이상 튀면(일시정지·장치 변경) 즉시 다시 맞춘다. API를 못 쓰면 `currentTime - outputLatency`로 대체한다.
- **판정 시간** = 입력 이벤트의 `event.timeStamp`를 곡 시간으로 바꾼 값 − (판정 오프셋 + 곡 오프셋). 렌더링 프레임과 무관하다. 키 입력은 이벤트 핸들러에서 즉시 판정한다.
- **표시 시간** = 지금(`performance.now()`)의 곡 시간 + (표시 오프셋 − 곡 오프셋). 노트 위치는 이 값으로 그린다.
- 오프셋 부호: 판정 오프셋 +20ms = "평균 20ms 늦게 치는 사람을 위한 보정", 표시 오프셋 +10ms = "노트를 10ms 앞당겨 그림". **곡 오프셋**(`settings.songOffsets`, 곡 ID마다 ±200ms)은 그 곡의 판정과 노트를 함께 같은 쪽으로 옮기고 채보·ID·기록은 그대로 둔다. 곡 시간이라 다른 재생 속도의 연습에서도 같은 ms만큼 옮긴다(실제 ms인 판정·표시 오프셋은 속도만큼 늘어난다). 플레이 중 오프셋을 바꾸면(− / =, 싱크 테스트의 키) 트랙·HUD를 다시 배치하지 않고 그에 딸린 값(첫 노트가 보이는 시각, 입력 오프셋)만 다시 계산하며, 판정 오프셋·곡 오프셋의 변화는 몇 번째 판정 뒤에 얼마인지(`PlayOutcome.offsets.shifts`)로 남겨 결과의 오프셋 추천이 그 전 판정을 바뀐 만큼 빼고 계산한다.
- **늦은 미스 판정**은 프레임 갱신에서 하되, 아직 처리되지 않은 입력 이벤트가 있을 수 있으므로 `missMarginMs`(50ms)만큼 늦게 확정한다. 입력이 들어오면 그 레인의 지난 노트를 먼저 정리한 뒤 판정한다.
- **리드인**: 첫 노트가 2초보다 빠르면 오디오 시작 전에 대기 시간을 넣는다. 이 동안 곡 시간은 음수다. 연습은 시작과 반복마다 첫 노트 3초 전과 그 노트가 SUDDEN+ 아래로 보이기 1초 전 중 이른 때부터 시작하고(`ui/practiceLead.ts`, 음악이 없으면 무음), 다른 재생 속도면 가장 느린 SPEED의 리드인만큼 앞 음원을 스트레치해 둔다. 첫 노트가 5초 넘게 남으면 Enter(또는 패드 FEVER 버튼)로 READY가 시작하는 곳(첫 노트 2.5초 전 이내)까지 건너뛴다. 첫 노트 전에는 판정할 것이 없어 결과가 같다.
- **창을 벗어나면 일시정지**(`pauseOnBlur`, 기본 켬): 내 플레이(오토·리플레이 아님)는 창이 포커스를 잃거나 가려지면 일시정지하고, 그런 상태에서 시작한(다시 한) 플레이는 일시정지로 시작한다.
- **STOP**(가져온 BMS·bmson): 박 시계가 멈추는 구간. 노트의 `t`는 STOP을 포함한 값이라 판정에는 영향이 없고, BPM 연동 스크롤에서만 그동안 노트가 멈춘다. 서버·클라이언트의 TempoMap이 같은 규칙(STOP 박에 있는 노트는 STOP이 시작할 때)을 쓴다.
- **게임패드 입력 시각**: 키보드의 `event.timeStamp` 대신 `Gamepad.timestamp`(브라우저가 패드 보고를 받은 시각, `performance.now()`와 같은 시간축)를 같은 변환에 넣는다. 값이 없거나 100ms보다 오래됐으면 읽은 시각을 쓴다.
- **가져온 키음**: BGM 채널을 렌더한 버퍼가 곡 시계의 기준이다(일반 곡의 `audio.flac` 자리). 노트 소리는 누른 순간(그 시각은 이미 지났으므로 곧바로), 오토 플레이는 `contextTimeForSong(t)`에 미리 예약해 노트 시각에 정확히 낸다. 노트 소리의 크기는 서버가 정한 게인(전체 믹스가 클리핑 없게)의 1.2배다(키음 버스, `AudioEngine.setKeysoundGain`).
- **생성 채보 키음**: 노트의 10% 이상이 따르는 스템이 키음 스템이 된다. 키음 스템마다 믹스와 길이가 같은 스템 버퍼를 믹스와 같은 `start(when)`에 위상을 뒤집어(게인 −1) 키음 구간에서만 더하므로, 반주 버퍼를 따로 만들지 않아도 배경 = 믹스 − 키음 스템이 된다. 노트를 치면 그 노트의 조각(같은 스템 버퍼의 [노트, 다음 노트) 구간, 30ms 안의 동치는 한 조각)을 곧바로 내고, 오토 플레이는 `contextTimeForSong(t)`에 예약한다. 조각은 3ms 일찍 시작해 앞 조각이나 배경과 크로스페이드하므로 제때 다 맞히면 원곡이 샘플 단위로 복원된다(OfflineAudioContext E2E에서 오차 < 1e-4). 플레이에서는 키음 버스가 조각을 1.2배(`KEYSOUND_BOOST`)로 내므로, 다 맞히면 키음 스템만 원곡보다 20% 큰 곡이 된다(크로스페이드 동안 1배에서 1.2배로 이어진다). 같은 스템의 새 조각은 이전 조각을 끊는다. 연습 모드는 믹스와 스템을 함께 스트레치한다. 곡 시간·판정은 믹스 소스 기준이다. 스템은 분석이 끝나면 서버가 백그라운드로 분리해 두므로(곡마다 약 100MB) 보통 플레이 전에 준비돼 있다.
- **출력 리미터**: 음악(키음 포함)과 타격음은 스피커로 가기 전에 소프트 리미터(`softLimiter`: WaveShaper, oversample none)를 지난다. 0.9까지는 그대로 두고, 그 위는 tanh 어깨로 눌러 1을 넘지 않는다(1 → 0.976, 1.2 → 0.9995). 샘플마다 곡선을 지날 뿐이라 지연이 없어 곡 시계·판정에 영향이 없다(DynamicsCompressor는 미리 보는 만큼 음악이 곡 시계보다 늦게 나서 쓰지 않는다). 음악 볼륨 기본 90%에서는 꽉 차게 녹음된 원곡도 0.9를 넘지 않아 손대지 않고, 1.2배 키음이 그런 곡 위에 겹친 순간만 누른다.

## 5. 판정 모델 (DJMAX RESPECT V 기준)

- 판정 구간(±ms, NORMAL): MAX 100% 41.67 / 90% 60 / 80% 78 / 70~20% 보간 / 10% 160 / 1% 180. HARD는 ×1/2, MAX JUDGEMENT는 ×1/4.
- 입력 처리(레인별): 그 레인에서 아직 판정되지 않은 가장 이른 노트를 대상으로 한다.
  - |오차| ≤ 1% 구간 → 해당 등급.
  - 1% 구간보다 이르고 간접 미스 구간(1% + 40ms × 배율) 이내 → 노트를 소모하며 BREAK.
  - 그보다 이르면 무시(빈 입력).
- 롱노트: 시작은 타이밍 판정 → 누르는 동안 1/4박마다 콤보 틱 → 끝까지 누르고 있으면 끝 판정 MAX 100% → 끝 100ms 이전에 떼면 끝 판정 BREAK. 시작이 BREAK면 끝도 BREAK.
- 콤보: 판정 대상(일반 노트, 롱노트 시작, 롱노트 끝)과 틱마다 +1. BREAK에서만 0(EX-SCORE 룰셋은 BAD에서도 0).
- 정확도(Rate) = 판정 %의 평균. 점수 = Rate × 10,000 (1,000,000점 만점).
- 사이드 트랙(FX 레인)의 노트를 놓치면 BREAK가 아니라 MAX 1%다(콤보 유지, 게이지 변화 없음, DJMAX PC 규칙). `judgement.json`의 `sideMissPercent`.
- 게이지(`config/gauge.json`): 판정 %에 비례해 회복하고 MAX 1%는 변화 없음.
  - 회복형(ASSIST EASY · EASY · NORMAL): 20%에서 시작, 총 회복량 TOTAL = 160 + 0.16 × 판정 수(최대 320), BREAK −2.5 / −4 / −5%. 끝날 때 클리어 선(60 / 80 / 80%) 이상이면 클리어.
  - 생존형(HARD · EX-HARD · HAZARD): 100%에서 시작, 판정마다 고정 회복, BREAK −9 / −18 / −100%(HARD는 30% 미만에서 피해 절반). 0%가 되는 순간 실패하고 곡이 멈춘다(음악 페이드아웃 → FAILED). 끝까지 버티면 클리어.
- 클리어 램프(낮은 것부터): FAILED < ASSIST CLEAR < EASY CLEAR < CLEAR < HARD CLEAR < EX-HARD CLEAR < MAX COMBO(콤보 끊김 없음) < PERFECT PLAY(전부 MAX 100%). 서버도 같은 순서(`gauge.json`의 `lampOrder`)로 최고 램프를 고른다.
- 점수 규칙(`config/rulesets.json`)은 DJMAX 판정 %를 표기·점수로 바꾸는 층이다.
  - 정밀 %(RESPECT): MAX 100% ~ 1% / BREAK, 점수 = Rate × 10,000.
  - 등급형(GRADE, EZ2ON 참고): PERFECT ≥100% · GREAT ≥70% · GOOD ≥10% · BAD ≥1% / MISS, 가중치 1 / 0.75 / 0.4 / 0.1로 1,000,000점 환산.
  - EX-SCORE(BMS 참고): PERFECT 2점 · GREAT 1점 · GOOD · BAD 0점 / POOR, BAD와 POOR에서 콤보가 끊긴다. 등급 AAA(8/9) ~ F.
  - 기본 점수(정밀 % 점수)는 점수 규칙과 무관하게 항상 같이 저장하고, 등급형의 가중 점수와 EX-SCORE는 기록의 `detail`에 남긴다. 결과 화면은 점수 규칙의 대표 숫자로 같은 판정 모드의 최고(서버의 `byMode`)와 비교하고, 램프 갱신은 선곡에 보이는 채보 전체의 램프와 비교한다. 최소 BREAK는 끝까지 친 판만 센다(게이지로 중간에 끝난 판은 `detail.failedAtMs`).
  - 페이스메이커는 화면의 점수와 같은 단위(기본 점수 · 가중 점수 · 목표 비율의 EX-SCORE)로 비교한다. 내 최고 기록은 그 판의 리플레이를 지금 채보 배치와 그 판의 판정 설정으로 다시 판정해(`engine/replay.replayScores`) 판정마다 따라가고, 리플레이가 없으면 정밀 %에서만 기본 점수의 직선을 쓴다.
- FEVER(`config/fever.json`): 판정 %만큼 FEVER 게이지가 차고(46노트 MAX 100%면 가득), 가득 차면 자동(또는 수동: FEVER 키, 기본 Enter)으로 14.5초간 발동. BREAK 없이 이어 가면 다음 배율이 x2 → x5까지 오르고, 발동 중 BREAK가 나면 끝나며 배율이 x2로 돌아간다. 보너스는 기본 점수와 따로 표시한다.
- 연습 모드: 재생 속도 r(0.5~1.5)에서 곡 시간은 실제 시간의 r배로 흐른다. 판정 구간·롱노트 유예·미스 여유를 곡 시간으로 ×r 해서 **실제 시간 기준 판정 폭이 그대로** 유지되고, 결과의 오차(ms)도 실제 시간으로 되돌려 보여 준다. 게이지는 실패 없는 NORMAL, 기록은 저장하지 않는다. 에디터의 커서부터 테스트는 재생 속도 ×1·반복 없는 연습으로, 배치 없이 기본 게이지·FEVER로 돈다(`ui/playRules.playedSettings`, 화면 이름 "에디터 테스트").

## 6. 렌더링 모델 (SDVX식 3D 트랙)

- 좌표계: 트랙은 y=0 평면, 판정선은 z=0(판정선 위치가 있으면 z = −`liftShare`(판정선 위치) × trackLength: 판정선 위치 100%가 트랙의 200px(`JUDGE_LINE_SPAN_PX`)이라 −20%는 기어 위 간격 40px만큼 내려 판정선이 기어에 붙고, +50%는 100px 올린다), 트랙은 −z 방향으로 `trackLength`(40)만큼 뻗는다. 트랙 폭 `trackWidth`(8)를 레인 폭 비율로 나눈다(스크래치 1.6배, 별도 레인일 때 사이드 트랙 0.75배). 사이드 노트는 반쪽 덮기로 그려(`render/layout.computeTrackGeometry`의 `sideNotes: 'half'`, 설정은 늘 이 값) 사이드 레인은 폭을 차지하지 않아 건반 레인이 트랙 전체를 사이드 없는 모드(4K·6K)처럼 나누고, FXL·FXR(`sideL`·`sideR` 색으로 정함, 모드의 레인 순서와 무관)은 건반 레인의 왼쪽·오른쪽 절반을 덮는다. 레인 번호·키·판정은 그대로다.
- 카메라: `(0, height, distance)`에서 `(0, 0, −lookAhead)`를 바라보는 원근 카메라. 프리셋 FLAT / SDVX / LOW와 아래의 PLANE(`config/camera.json`, 기본 SDVX). 원근은 그대로 두고 화면만 위아래로 옮겨(뷰 오프셋) LIFT 없는 판정선을 화면 높이의 `judgeLineY`(77%)에 둔다. 그 아래는 기어 하단이다. 카메라의 near 평면은 거리에 따라(거리의 1/4) 두어 얇은 트랙 층의 깊이 순서를 지키고, far 평면은 트랙 끝을 덮는다. FLAT은 트랙 끝이 화면 위 약 4.6% 안쪽에 오게 맞췄다. PLANE(평면)은 같은 자리에서 평행 광선으로 보는 직교 카메라(`projection: "orthographic"`, `render/TrackRenderer.PlaneCamera`)라 레일이 화면에서 평행하고 노트가 화면 위에서 아래까지 같은 빠르기로 내려온다. 시야각 대신 `fov`의 원근 카메라가 lookAhead 지점에서 담는 높이만큼 화면에 담아, 같은 뷰 오프셋의 판정선 맞추기·줌·미리보기 맞춤이 원근 카메라와 같은 식으로 돈다. 판정선과 트랙 끝(화면 위 약 4.4%)의 높이가 정해져 있어 내려다보는 각도(약 15.2°)가 트랙 폭을 정한다(1280x720에서 판정선 폭 약 398px). 깊이 범위는 트랙과 그 위에 선 것만 덮어 고른 깊이 단계로도 층이 섞이지 않는다. 트랙이 화면에서 납작해지는 만큼 기어의 표시등 줄을 깊게 잡아(`keyRow`) 둥근 표시등이 원근 카메라에서처럼 둥글고 같은 크기다.
- **기어**(`render/deckArt.ts`, 그림은 `render/styleArt.ts`가 고름): 고른 기어(`style.deck`, 설정 `parts.deck`)는 이름 붙일 수 있는 사물 하나로, 판정선과 그 아래 받침, 트랙의 좌우 테두리(아래 "트랙 테두리"), HUD의 게이지·점수판·숫자 글꼴(`render/gearHud.ts`, 아래 FEVER에도 받침은 그대로다. 기어의 불빛(`render/gearLights.ts`)은 곡의 마디와 박자(`beatClock`: 마디선 시각에서 마디, 마디당 네 박, FEVER 여부)에 따라 켜지는 빛 조각들이다: 기어마다 빛(`GEAR_LIGHTS`: 둥근 빛 · 고른 빛 · 링(서 있는 부품에 가린 호는 뺌) · 반짝임, 받침 그림의 px에서 자리와 크기, 박자에 따른 밝기)과 화면(키보드의 OLED: 막대가 8분음표마다 바뀔 때만 다시 그림)을 받침 위에 더하기로 겹치고(`GearLightLayer`, renderOrder 9.06–9.07) 매 프레임 불투명도만 바꾼다. 부품 안에서 비치는 빛(키보드 방향키의 홈, 기본의 스피커 구멍, 나전칠기의 자개)은 받침 그림에서 만든 빛 마스크(`<기어>/glow`, `build_gears.py`의 `glow_mask`: 홈의 어두운 틈 · 키캡 윤곽 밖, 구멍, 옅고 밝은 자개)를 빛 그림에 곱해 그 부분에서만 보인다. 코드로 그린 받침(평면 카메라)에서는 판이 부품마다 남긴 자리(`DeckSpec.marks`, `mark`)에 빛을 얹고(링은 위에서 보이므로 한 바퀴, 방향키의 빛은 표시한 홈 상자 안 · 키 상자 밖의 좁은 틈에 고르게: `fill`), 키보드 판에는 방향키 홈을 그린다. 판정선은 레이저처럼 빛이 조금씩 떨리고 밝은 점이 선을 따라 지나가며(`shimmerJudge`), 테두리는 마디마다 FEVER 불빛을 띠로 트랙 끝에서 기어까지 지나가게 보여 준다(`sweepBorders`: 테두리 윗면과 벽 안쪽 면에 FEVER 그림을 띠 모양 알파 맵으로). 번쩍임 줄이기에서는 깜빡임 없이 천천히(차례도 부드럽게 오르내림: `softTurn`). 그림은 제 비율대로(동전 투입구 558×384, 스위치 320×368, 황동 명판 912×192, 토글 495×512) 그린다. 방향키 캡과 고무 버튼의 링, 켜진 사각 버튼은 무채색 그림 하나에 곱하기로 색을 입힌다(`dye`). 부품은 그림(`client/public/media/gears/<기어>/`, `scripts/assets/build_gears.py`가 만듦: 생성한 사물을 잘라 테두리에 비친 마젠타 바탕을 걷어내고(`despill`), 재질은 시드를 정한 잡음으로)에서, 그림이 없는 부품은 같은 자리에 코드로 그린다(`GearArt`: 부품마다 따로; 모든 기어의 받침 그림 `deck`, 기본은 `jog`, 오락실 기체는 `plate`·`joystick`·`button`·`coin`, 리시버는 `plate`·`knob`·`switch`, 나전칠기는 `lid`·`lock`과 테두리의 `frame`, 커스텀 키보드는 `plate`·`knob`·`keycap`·`brass`, 레이싱 휠은 `plate`·`rotary`·`button`, 우주선 계기판은 `plate`·`selector`·`toggle`·`button`과 테두리의 `frame`). 스킨의 라인·악기색 기어(`line`·`stem`, 지금은 고를 수 없음)만 레인마다의 빛(`KEY_PAINT`, 레인 색으로 칠하는 틴트 그림)을 판 위쪽 줄에 두고 키가 눌린 동안 켠다: 빛이 기준 육각형(`referenceReach`)보다 크면 크기를 그대로 두고 그 줄을 더 아래에 놓아 어느 레인에서도 판정선에 더 가깝지 않다(`deckArt.rowDrop`). 반쪽 덮기의 사이드 레인은 그 줄에 자리가 없고 줄 아래에 그 절반 폭의 막대(`deckRows`: `SIDE_ROW` 깊이, `SIDE_GAP` 간격, 트랙이 납작한 카메라에서는 줄처럼 깊게)로 켜지며, 꺼져 있으면 판정선 바로 아래의 사이드 노트로 읽히지 않게 양 끝만 보인다(`SIDE_PAINT`, 판의 아래쪽 그림은 막대 아래부터 `lowerTop`). 예전의 레인마다의 건반 그림(기본의 패드, 오락실 기체의 턴테이블, 나전칠기의 자개 판)은 지웠다. 예전의 세트 기어 다섯(아케이드·믹서·크리스털·네온·그랜드 피아노)과 그보다 앞의 코드 기어 7종도 지웠다: 저장한 값은 기본 기어로(`sanitizeParts`), 예전 스킨 JSON의 `style.deck`은 지운 세트 기어면 기본 기어(`DECK_RENAMES`), 그 밖에는 그 스킨의 캡(`CAP_DECKS`)이나 라인으로 읽는다. 기어마다 한 가지 모습이다(기어 색 설정은 없앴고 예전 저장값의 `deckColour`는 버린다).
- **판정선**: 고르는 기어는 모두 같은 판정선이다(`GEAR_JUDGE`, DJMAX처럼): 노트 그림이 놓이는 높이(바로 위)에 두께 16px의 붉은 선(`#ff2b3b`)과 그 가운데 밝은 심(선 두께의 28%), 위아래로 퍼지는 붉은 빛(`judgeGlowTexture`, 퍼짐 22px)을 그리고, 받침은 선 가운데에서 `deckTop`(선 아래 3px) + 40px(`gap`) 아래에서 시작한다. 그 사이로 레인이 이어져 판정선을 지나간 노트가 받침이 시작하는 곳에서 잘려 판에 가려지고(놓친 노트가 판정선을 지나 사라짐), 빛의 아래쪽 절반도 보인다. 선과 빛은 트랙이 납작하게 보이는 카메라(평면)에서 그만큼 트랙 방향으로 길게 그려(`judgeFit`: 판정선에서 트랙의 납작함 ÷ 1.3, 1 이상, 판정선 묶음을 트랙 방향으로 늘림) 어느 카메라에서나 화면에서 같은 두께로 보인다. 간격은 트랙의 다른 구간처럼 늘리지 않아(평면 카메라에서는 그만큼 얇아 보임) 판정선 위치 −20%가 어느 카메라에서나 판정선을 기어에 붙인다. FEVER에는 빛만 배율의 색으로 바뀐다. 판정 순간 탭 노트의 가운데가 판정선 가운데에 오고(모든 카메라), 판정선은 화면 높이의 `judgeLineY`(77%)에 있다. 판정선은 노트·커버 위, 타격 이펙트 아래에 그린다. 스킨의 라인·악기색 기어(고를 수 없음)는 스킨의 판정선을 쓴다: 기본 스킨은 모두 네온과 같은 두께 6px 선과 그 위로 은은한 빛(`judgeGlow`, 스트리트는 노랑·아케이드는 주황, 모노는 빛 없음)이고 두 번째 선은 없으며, 기어 하단은 판정선 가운데에서 6px 아래부터(사용자 스킨의 굵은 선은 선 아래 3px, `under` 선은 그 아래 3px) 시작한다. 사용자 스킨의 `under`/`over` 선은 판정선에 붙여 그린다. 고르는 기어가 판정선을 정하므로 스킨의 판정선 색(`judgeLine`·`judgeGlow`)과 그림(`textures.judgeLine`)은 지금 플레이에 쓰이지 않는다.
- 노트 위치(`engine/scroll.ts`): `z = 판정선 z − 거리`. 모든 노트는 한 기준점을 쓴다(`render/layout.noteSpan`): 탭은 제 시각에 가운데가 오고, 롱노트는 시작 시각 탭의 가까운 끝부터 끝 시각 탭의 먼 끝까지라 어느 SPEED·노트 깊이에서도 같은 시각의 탭과 롱노트 머리가 한 줄로 맞는다. 시간 고정 스크롤은 `거리 = (노트 시간 − 표시 시간) × trackLength / 가시 시간`, BPM 연동 스크롤은 박 차이 × 주 BPM의 박 길이로 거리를 잡아 빠른 구간에서 노트도 빨라진다(주 BPM 구간에서는 두 방식이 같다). 배속은 월드 좌표의 속도로 정의되므로 원근과 무관하게 일정하다.
- 레인 커버: 노트 등장 위치(SUDDEN+, 먼 쪽) · 노트 사라짐 위치(HIDDEN+, 판정선 쪽)는 노트·롱노트·마디선 재질에 공유 클리핑 평면 두 개를 걸어 정확히 잘라내고, 그 위에 커버 판과 경계선을 그린다. 판정선 위치(LIFT, 설정 `judgeLinePosition`, −20%~+50%)는 판정선·키 빔·이펙트를 위아래로 옮긴다: 고르는 기어는 판정선 위치 0%의 자리(화면 아래)에 그대로 있고(`deckTopZ`), 올리면 올라간 판정선 아래 간격이 끝나는 곳부터 기어까지를 노트 등장 위치와 같은 커버(`liftCover`)로 덮으며(놓친 노트는 커버가 시작하는 곳에서 잘림), 내리면 간격이 줄어 −20%에서 판정선이 기어에 붙는다(놓친 노트는 기어에서 잘림, `notesEndZ`). 예전 설정의 LIFT(트랙 길이의 몫)는 그 판정선 자리를 범위 안에서 판정선 위치로 옮겨 읽는다. 스킨의 기어(고를 수 없음)는 판정선을 따라 움직여 그 아래를 판으로 덮는다. 플레이 중 단축키로 바꾸면 클리핑 평면 상수만 움직인다(재컴파일 없음). "보이는 시간 유지"를 켜면 커버·판정선 위치를 움직일 때 노트 속도를 다시 계산해 녹색 숫자를 유지한다.
- **트랙 테두리**(레일 자리, `TrackRenderer.buildRails`): 트랙의 양 가장자리를 트랙 끝부터 기어 아래까지 고른 기어의 테두리로 그린다(`styleArt.borderLookOf`가 고르는 `SideLook`을 `deckArt.paintBorder`가 타일 한 장에 칠하고 트랙을 따라 반복, 거울 반복이라 결에 이음매가 없고 먼 곳은 밉맵). 기어는 저마다 제 폭(`SideLook.width`, HUD가 비켜 두는 폭 `railPx`와 같음)과 타일 길이(`tile`)의 테두리를 칠한다(`paint`, 오른쪽은 왼쪽을 뒤집어 조금 그늘지게): 기본은 그래파이트(14px)에 하늘색 선, 오락실 기체는 검은 플라스틱 측판(28px)에 크롬 몰딩과 호박색 LED 점, 빈티지 리시버는 월넛(30px)에 알루미늄 몰딩, 나전칠기는 흑칠(30px) 가운데 금선 두 줄 사이의 자개 당초문(생성한 띠에서 덩굴 한 줄기만 잘라 씀), 커스텀 키보드는 차콜 알루미늄(26px)에 폴리싱한 모서리와 그 아래 주황 선, 타일마다 육각 나사, 레이싱 휠은 카본(30px)에 빨간 스티치의 스웨이드 띠와 빨간 선, 우주선 계기판은 금박 단열재(30px, 생성한 금박 텍스처에서 1:6 띠를 잘라 늘이지 않으려고 타일을 120px로)에 바깥쪽 노란 손잡이와 안쪽 회색 레일. FEVER에는 테두리의 다른 그림(`lit`: 하늘색 선이 밝게, LED 점이 모두 켜짐, 몰딩이 호박색, 자개가 밝게, 주황 선이 밝게, 스티치와 빨간 선이 밝게, 레일의 램프가 켜짐). 고른 기어의 테두리는 벽으로 선다(`SideLook.height`, 기어마다 16–32px): 윗면을 그 높이로 올리고, 레인 가장자리에서 트랙까지 안쪽 면(`TrackRenderer.buildWall`, 트랙 방향으로 눕힌 판을 레인 쪽으로 세움)을 기어마다의 재질(`SideLook.face`: 그래파이트와 하늘색 선, ABS와 크롬, 월넛과 알루미늄, 흑칠과 금선, 알루미늄 모서리, 스웨이드와 빨간 스티치, 금박)로 칠해(`paintFace`: 위 모서리 빛, 발치 그늘, 왼쪽 위 빛을 등진 왼쪽 벽은 어둡게, 오른쪽 벽은 밝게) FEVER 그림도 따로 둔다. 벽은 레인에 그림자를 드리운다(왼쪽 벽은 레인 쪽으로 넓게, 오른쪽 벽은 발치에 선, 노트 · 마디선 아래에 그림). 원근 카메라에서 벽 윗면이 바깥쪽으로 더 나와 보이는 만큼 HUD의 옆 자리를 바깥으로 민다(`planeAs`의 `sideOut`); 위에서 내려다보는 평면 카메라(정사영)에서는 안쪽 면이 옆으로 누워 보이지 않는다.으로 바꾸고(텍스처를 한 번 바꿀 뿐 매 프레임 일은 없음), FEVER 색을 더하지 않는다. 그림이 없으면 같은 모양을 코드로 칠한다. 기어가 제 테두리를 그리면 스킨의 레일 폭·레일 빛·바깥 벽(아케이드·스트리트)은 쓰지 않는다. 스킨의 라인·악기색 기어(고를 수 없음)는 예전처럼 판의 색으로 스킨의 레일 폭에 그리고, 스킨에 레일 빛(`style.rails.glow`)이 있으면 테두리의 모서리 색으로 빛나며 FEVER 색을 더한다.
- FEVER 중에는 트랙에 배율별 색(x2 하늘 · x3 초록 · x4 노랑 · x5 분홍)을 일정하게 더하고(박과 무관한 깜빡임 없음, 끝나기 전 1/5 동안 흐려짐) 트랙 테두리 위에 같은 색을 더하며(테두리 빛도 그 색) 판정선 빛을 같은 색으로 바꾼다(FEVER가 시작하고 끝날 때만 다시 칠함). "번쩍임 줄이기"는 맥동·타격 이펙트·키 빔을 약하게 한다. 색각 보정 팔레트(Okabe–Ito)는 레인·판정 색을 함께 바꾼다.
- 바닥만 트랙 길이의 `fogStart`(기본 0.55, PLANE 0.835)부터 끝까지 안개로 흐려지고, 노트·롱노트는 안개 없이 트랙 끝에서 잘려 보이는 시간 내내 또렷하다(트랙 끝 너머로 이어지는 롱노트는 끝 테두리 없이 열린 채 잘린다). 레인 구분선·마디선으로 원근 속에서도 박을 읽기 쉽게 한다.
- 마디선은 마디마다 트랙을 가로지르는 선이다(설정 "마디선", 기본 켬). 트랙 위 두께가 일정하면 멀리서는 사라지므로, 매 프레임 카메라 투영으로 두께를 다시 잡아 판정선부터 트랙 끝까지 화면에서 약 4px(`BAR_LINE_PX`)로 보이게 한다(`render/TrackRenderer.barLineDepth`). 색은 스킨의 `bar`(트랙 가까운 쪽 색 위에 흰색 35%), 불투명도 0.95라 레인 구분선보다 굵고 밝아 마디가 구분선과 섞이지 않는다. 노트·롱노트 아래에 그린다.
- 롱노트는 몸통만 그린다. 가까운 끝이 누를 시각 탭의 가까운 끝, 먼 끝이 뗄 시각 탭의 먼 끝이고, 누르는 동안은 몸통이 판정선에서 시작한다. 양 끝에 노트 모양을 붙이면 단노트로 읽혀 붙이지 않는다. 끝은 몸통 자신의 끝 모양으로 닫는다(`LONG_PAINT`의 `end`): 기본은 밝은 테두리, 레일(메카 챔퍼 계열)은 45°로 깎은 모서리와 밝은 테, 캡슐(원형 계열)은 반원, 별빛(별 계열)은 한 갈래 별처럼 뾰족한 끝. 몸통은 탭 노트와 같은 레인 폭의 90%이고, 탭보다 조금 어둡고 차분하다.
- 노트·롱노트 몸통·마디선은 오브젝트 풀에서 꺼내 쓰고, 화면에 보이는 구간만 갱신한다.
- **반쪽 덮기의 사이드 노트**: 그 절반의 96% 폭 막대를 건반 롱노트·탭보다 먼저(`renderOrder` 2.2–2.3, 마디선 위) 반투명으로, 깊이를 쓰지 않고 그려 위에 오는 건반 노트가 늘 보인다. 탭은 제 시각에 가운데가 오고 같은 시각 건반 탭의 앞뒤 끝보다 0.18만큼 길어 그 절반을 다 덮는 화음 아래에서도 밝은 앞뒤 가장자리가 보이고, 롱노트는 그런 탭의 가까운 끝부터 먼 끝까지 머리·끝의 밝은 띠와 흐린 몸통이다(누르는 동안 밝게, 놓치면 회색). 색은 스킨의 사이드 레인 색(`sideL`·`sideR`, 색각 보정 팔레트 포함)이다. 사용자 스킨의 `side`·`longBody` 텍스처와 노트 모양은 쓰지 않는다. 사이드 노트(`style.side`, 설정 → 기어 → 사이드 노트)가 `dots`면 탭·몸통·끝을 LED 점으로 그린다(`sideDotsTap`·`sideDotsBody`·`sideDotsEnd`: 건반 한 레인에 점 5개, 앞뒤 가장자리 줄은 밝게, 몸통 그림은 반쪽 폭만큼 깊어 점이 따라 흐른다). 별도 레인(`sideNotes: 'lanes'`, 지금은 설정으로 고를 수 없음)의 사이드 노트도 `dots`면 점 세 줄의 탭(가운데 줄이 그 시각)과 네 줄마다 밝은 몸통(`DOTS_LONG`)이다. SUDDEN+·HIDDEN+·LIFT·기어 판이 노트처럼 자른다. 타격은 그 절반 폭의 띠와 조금 올라오는 빛(건반 효과 아래, 누르는 동안은 낮고 일정), 키 빔은 그 절반을 건반 빔의 1/4 밝기로 덮는다.
- **타격 효과**(모양은 설정 → 기어 → 타격 효과, `parts.hit`, 기본 flash): 고를 수 있는 9종(flash·flare·bubbles·grid와 세트의 mecha·club·crystal·neon·piano)은 모두 그림의 플립북(치는 순간 16칸 60fps · 누르는 동안 16칸 반복 24fps, 아래 스킨 텍스처)으로 그리고, 판정선 위로는 짧게만 남는다(grid는 판정선 아래에만). 플립북이 없을 때의 코드 그림(`tintArt.effectSheet`)은 flash·flare·bubbles·grid가 제 모양, 세트의 효과는 flash이고(`DRAWN_AS`), stemflash(지금은 고를 수 없음)는 코드로만 그린다. 코드로만 그리던 star·bomb·hex·shards·wave·spark·shutter는 지웠다(저장한 값은 flash로). 모든 타격·롱노트 효과는 레일에서 잘린다. 설정 `hitEffectSize`(설정 → 연출·배경 → 타격 효과 크기: 보통 / 작게 / 끄기)의 작게는 약 1.2레인 폭 이내(반쪽 덮기의 사이드 타격은 폭은 절반 그대로 낮게만), 끄기는 그리지 않는다.
- **HUD**(`ui/Hud.ts`): 판정·콤보 텍스트는 트랙 위 3D 지점을 화면 좌표로 투영해 DOM HUD로 그린다(`judgementOpacity` 1 / 0.7 / 0.4로 비치게, 판정이 커졌다 줄어드는 연출은 1.1배에서 시작). `errorBar`면 판정 아래 같은 평면에 판정 오차 막대를 둔다(양 끝이 판정 모드의 가장 넓은 범위, 옅은 가운데 칸이 최고 판정 범위, 눈금 20개를 돌려 쓰며 판정 때만 transform·opacity를 바꿈, 최근 20개의 평균은 긴 선, 다시 하기·연습 반복에서 비움). 기어 왼쪽 SPEED 위의 점수판(SCORE · 페이스메이커 · RATE · MAX COMBO, `judgeCounter`면 그 점수 규칙의 놓친 수와 FAST·SLOW 수)은 줄마다 그 자리의 화면에서 크기와 트랙 방향 늘임을 정해(`uprightAt`, 세로 성분만 재고 4배까지) 맨 위 줄도 라벨 12px 이상으로 읽히고, 모자라면 라벨을 숫자 위로 쌓고, 그래도 모자라면(좁은 창의 아주 넓은 기어) 트랙을 떠나 화면 왼쪽 아래에 똑바로 선다. 기어 왼쪽의 얇은 진행 바(500단계)와 마지막 노트까지 남은 시간, 템포가 바뀌는 곡이나 BPM 연동 스크롤이면 SPEED 아래 들리는 BPM(`TempoMap.bpmChanges`), 게이지는 숫자·칸 모두 내림(`gaugeShown`, `gaugeCells`, 클리어 선 위 칸은 MAX 색). 왼쪽 위 곡 아래 줄에 AUTO · REPLAY · 연습 · 에디터 테스트와 NORMAL이 아닌 판정, 로딩 카드에 기본값이 아닌 규칙 칩. 고른 기어가 기어 옆 HUD를 꾸민다(`render/gearHud.ts`, HUD 뿌리의 `data-gear`와 `styles.css`의 기어별 토큰): 게이지(기본은 하늘색 칸, 오락실 기체는 초록→노랑→빨강 LED 칸과 그 위 'GROOVE', 나전칠기는 자개 매화 칸(마스크)과 그 위 '흥', 빈티지 리시버는 칸 대신 'SIGNAL' 바늘 미터: SVG 하나를 점수판 줄처럼 똑바로 세우고 게이지가 바뀔 때만 바늘의 회전을 씀, 클리어부터 빨간 구간, 커스텀 키보드는 흰 칸과 클리어 선 위 주황 칸에 'CHARGE', 레이싱 휠은 클리어 선 아래 호박색·위 흰 칸에 'FUEL', 우주선 계기판은 초록 칸에 'O2'), 점수판 하우징(`.hud-panel-plate`: 점수판 줄들 아래 트랙에 누운 판, 스모크 유리·볼트 박은 아크릴·은색 테 검은 유리·금테 흑칠·차콜 테의 OLED·카본 테의 대시 화면·회색 베젤의 표시창), 숫자 글꼴과 색(DSEG7 7세그 빨강·호박색·초록, Cinzel 금색, Silkscreen 픽셀 흰색, Chakra Petch 기울어진 흰색), 판정·콤보 글꼴(`GEAR_TYPES`: 기본은 'MAX' 흰색에 '100%' 하늘색, 오락실 기체는 빨간 테의 흰 이탤릭과 빨간 7세그 콤보, 리시버는 따뜻한 흰 장체와 호박색 7세그 콤보, 나전칠기는 금색 세리프, 커스텀 키보드는 픽셀 글꼴의 크림색에 주황 밑줄, 레이싱 휠은 기울어진 흰 글자에 빨간 밑줄, 우주선 계기판은 흰 스텐실 판정과 초록 7세그 콤보; 설정 `hudType`이 `skin`이면 스킨의 글꼴). 모두 평면 채색과 선이고 플레이 중에 다시 그리는 것은 없다. 플레이 중 바꾼 값은 판정선 아래 기어 위에 한 번만 토스트("노트 속도 4.10", `ui/format.ts`의 `speedText`·`coverText`, HUD의 SPEED 표시는 그대로). READY는 첫 노트가 SUDDEN+ 아래로 보이기 1.5초 전부터(`ScrollModel.timeAt`), 다시 하기(F2·R)와 연습 반복마다 HUD를 처음 상태로(`Hud.reset`). 값은 바뀔 때만 DOM에 쓴다.
- 카메라 연출이 켜져 있으면 판정·콤보 글자를 매 프레임 현재 카메라(기울기·줌)로 다시 투영하고, 트랙이 기운 만큼 글자도 같이 돌린다. 왼쪽 위 곡 정보 판은 기어 왼쪽 가장자리 앞에서 끝난다(`Hud.fit`, 시작·창 크기·플레이 중 설정이 바뀔 때만): 채보의 카메라 연출이 트랙을 그쪽으로 가장 많이 기울이고 당기는 자세(`CameraFx.peak`)로 잰 자리라 연출 중에도 트랙을 가리지 않고(트랙 끝이 판정선만큼 넓은 PLANE의 4:3 화면 등), 그 자리가 난이도 칩보다 좁으면 판 전체를 줄인다.
- **카메라 연출**(`render/cameraFx.ts`): 채보의 tilt는 이전 기울기에서 새 값으로 smoothstep으로 옮겨 가 유지하고, zoom은 (1 − 진행률)²로 감쇠하는 펄스다. 매 프레임 기본 카메라 자세(쿼터니언·FOV)에 roll(최대 7°)과 FOV 축소(최대 7%)를 얹고, `frameCamera`가 바뀔 때마다 다시 맞춰 (들어 올린) 판정선 가운데가 제자리에 있고 기울기가 그 점을 중심으로 돈다(연출 없는 맞춤은 카메라·화면·LIFT가 바뀔 때까지 기억해 한 프레임에 투영 갱신 한 번). 판정 시각은 이와 무관하다. 직교 카메라(PLANE)는 눈이 없으므로 판정선 가운데를 지나는 시선 방향 축으로 카메라를 돌린다. 세기는 설정값(0–1, "번쩍임 줄이기"면 절반)을 곱한다. 수치는 `config/camera.json`의 `fx`.
- **스킨**(`render/skins.ts`): 레인 색 배치(키 모드 색·단색·무지개)와 트랙·구분선·마디선·판정선·커버·안개 색, 키 빔(`style.beam`), 레일 폭·빛의 유무(트랙 테두리는 기어의 것), 판정선 모양, 바닥 무늬, 레일 바깥 벽, 판정·콤보 글꼴(`style.type`). 노트·사이드 노트·기어·타격 효과는 스킨이 아니라 부위별 선택(아래)이 정한다. 스킨 정의에 남은 `style.note`·`deck`·`hit`은 `withParts`가 늘 바꿔 쓰므로, 악기색 스킨의 악기색 노트·기어·플래시(`stem`·`stemflash`)와 보석의 플립북 타격(`flipbook`)은 지금 그려지지 않고 악기색 스킨은 키 빔만 악기 색이다. 사용자 스킨의 `noteShape`(상자·납작·캡슐)·`hitEffect`(폭발·링·그림·없음)도 읽기만 한다. 코드로 그린 10종(기본·악기색·아케이드·클럽·스트리트·네온·크리스털·팝·보석·모노) + JSON 사용자 스킨(알 수 없는 값은 버리고 색은 `#rrggbb`만 받는다). 색각 보정 팔레트를 켜면 레인 색은 팔레트가 우선한다(노트 색이 기본일 때).
- **노트 모양**(`render/tintArt.ts`의 `NOTE_PAINT`): 기본 막대(`flat`)·악기색 막대(`stem`, 지금은 고를 수 없음)와 네 계열(메카 챔퍼 `chamfer`·원형 `round`·별 4각 `star4`·별 5각 `star5`), 계열마다 롱노트(`LONG_OF`: 레일·캡슐·별빛; 스킨에는 롱노트가 따로 없고 늘 노트의 계열). 노트 그림은 레인 종류(`NoteMark`: 흰·파란·금색 건반, 스크래치, 사이드)마다 따로 그려 메카 챔퍼·원형에는 표식(○△◇//)을, 별에는 파란·금색 건반에 꼭짓점을 더한다. 막대·판은 늘 같은 깊이(0.7)이고, 원형과 별은 판정선에서 제 모양(원형은 원)으로 보이도록 깊이를 카메라가 판정선에서 트랙을 누르는 비율에 맞춘다(`noteDepthOf`, 막대의 3배까지, 카메라·화면이 바뀌면 0.05 단위로 다시 맞추고 그림을 새로 그림, `TrackRenderer.fitNoteDepth`). 레인이 넓은 스크래치와 좁은 사이드 레인에서는 네 계열이 같은 비율을 지키도록 레인 폭만큼 깊거나 얕다(`laneDepthOf`, 기본·악기색 막대는 그대로). 예전 스킨 JSON의 노트 이름(gloss·thin·outline·chip·gem·pill·jewel 등)은 그 자리를 넘겨받은 계열로 읽고, 롱노트 이름은 읽지 않는다. 메카 챔퍼와 그 레일은 메카 세트의 그림이 있으면 그림으로 그린다(`styleArt.notePaintOf`·`longPaintOf`): 노트는 양 끝 캡과 가운데 표식이 화면에서 그림대로 보이게(`NOTE_STRETCH`만큼 트랙 방향으로 늘림) 두고 그 사이 금속과 LED 슬릿만 레인 폭에 맞게 늘이며(조각 경계는 정수 px), 사이드 탭은 끝 블록을 그대로 둔 막대(별도 레인으로 그릴 때의 사이드 노트는 가운데 격자 한 칸을 되풀이한 격자판)다. 레일은 몸통 타일과 끝을 그림에서 그리고 누르는 동안은 안에서 빛이 흐르는 그림으로 바꾼다(`LongPaint.held`). 원형 · 별 4각 · 별 5각은 클럽 · 크리스털 · 네온 세트의 그림으로 그린다: 레코드(표식은 레이블에 그려져 있음)와 네온 별(관 아래에 표식을 코드로)은 노트를 채우고 판정선에서 그림 비율대로 보이는 깊이(`styleArt.noteShapeOf`: 레코드 1, 별 488/500)이고, 크리스털의 긴 보석은 막대 깊이 안에 그림보다 조금 두툼하게(가운데에 표식을 새김, `noteShapeOf`가 `null`이면 막대 깊이) 그린다. 별도 레인의 사이드 노트는 세트의 짧은 사이드 판, 롱노트는 캡슐 · 프리즘 · 네온관 그림이다(`longPaintOf`가 노트 계열을 받음). 피아노(`piano`, 다섯째 계열, 롱노트 `key`)는 메카 챔퍼처럼 막대 깊이의 건반 앞판을 다섯 조각으로 그리고(둥근 양 끝과 표식은 그대로, 상감선만 늘임), 롱노트는 래커 건반이다.
- **부위별 선택**(`render/skins.ts`의 `SkinParts`·`withParts`, 설정 `parts`): 노트·사이드 노트·기어·타격 효과를 고르고, 어느 스킨에서나 늘 고른 것을 그린다(`withParts`가 스킨의 `style`에서 이 넷만 바꾸고 색·트랙·판정선·글꼴은 스킨 그대로; 판정·콤보 글꼴은 설정 `hudType`이 기어(기본)면 기어의 것, 아래 HUD). 기어 색은 고르지 않고(기어마다 한 가지 모습, 예전 저장값의 `deckColour`는 `sanitizeParts`가 버림), 기본값은 `flat`·`bar`·`standard`·`flash`(설정 화면에서 기본 · 기본 · 기본 · 플래시)이고 "스킨" 선택지는 없다. 고를 수 있는 것은 `PART_NOTES`·`PART_DECKS`·`PART_HITS`로, 악기색 노트·기어·플래시(`stem`·`stemflash`)와 라인 기어(`line`)는 스킨의 것이라 뺐다. 사이드 노트는 `bar`(기본, 비치는 막대)·`dots`(도트 매트릭스) 중 하나다. 예전에 저장한 `skin`이나 지금 고를 수 없는 값은 기본값으로 읽는다. 롱노트는 고르지 않고 늘 노트의 계열이다(`LONG_OF`). 플레이·설정 미리보기·표시 오프셋 맞추기가 `settings.skinOf`로 같은 스킨을 쓴다. 플레이 캔버스의 `data-style`에 그린 노트·롱노트·사이드·기어·효과가 적힌다(테스트용, 보이지 않음; 기본 부위면 어느 스킨에서나 `flat solid bar standard flash`).
- **노트 색**(`render/noteColors.ts`, 설정 `noteColors`·`colorPresets`): 프리셋이 키 모드마다 레인별 색(`#rrggbb`)을 가진다. `skin`(기본)은 팔레트와 스킨의 색(`laneColorsFor`)이고, 게임에 든 프리셋(`BUILTIN_PRESETS`: 오로라·앰버는 레인 역할별 색, 좌우 손은 레인을 치는 손별 색)은 바뀌지 않는다. 그 색을 바꾸면 `lanesOf`로 모든 키 모드의 색을 복사한 내 프리셋(`user-N`, "내 색 N", 20개까지)에 저장한다. `settings.laneColorsOf`가 플레이·설정 미리보기·표시 오프셋 맞추기·에디터에 같은 색을 준다. 렌더러는 색을 받아(`laneColors`) 노트·롱노트·레인 표시등·키 빔·바닥 색을 칠하고, 돌아가는 중에도 바꿀 수 있다(`setLaneColors`: 바닥과 키 빔은 바로, 색별로 캐시한 재질은 새로 만들고 옛 재질은 다음 프레임 뒤에 버려 셰이더가 다시 컴파일되지 않는다). 설정의 노트 색 탭(`ui/NoteColorsPanel.tsx`)은 색 상자·색상 막대를 끄는 동안과 HEX를 입력하는 동안 아직 저장하지 않은 색을 미리보기에만 보낸다(`GearPreview`의 `laneColors`). 색상은 HSV 정수로 따로 들고 있어 단계가 쌓여도 어긋나지 않고 회색도 색상을 잃지 않는다. 모두 초기화는 내 프리셋을 남긴다. 플레이 캔버스·미리보기의 `data-lane-colors`에 레인 색이 적힌다(테스트용, 보이지 않음).
- **스킨 텍스처**(`render/skinArt.ts`): 스킨의 `textures`가 부분(노트·사이드·스크래치·롱노트 몸통·판정선·레일·바닥·키 빔·타격 이펙트·롱노트 불꽃)마다 `client/public/media/manifest.json`의 텍스처를 고른다. 플레이 화면이 음원과 함께 미리 불러오고, 매니페스트가 없거나 파일이 없거나 깨지면(크기가 매니페스트와 다르면) 그 부분만 코드로 그린다. 텍스처는 모두 흑백이고 색은 스킨 색표로 곱한다. 같은 불러오기가 고른 부위를 그리는 그림(`styleArt.styleImageIds`: 네 계열 노트면 그 세트의 노트·롱노트·사이드, 그림으로 그린 기어면 표시등과 판(`<세트>/gear`); 매니페스트 이름은 `<세트>/<부위>`이고 크리스털 세트만 `gem/…` — `crystal/…`은 사용자 스킨이 부를 수 있는 예전 텍스처 세트)을 캔버스에 그릴 수 있게 색 관리 없이 풀어 두고(`createImageBitmap`, 틴트 그림의 채널은 색이 아니라 양), 고른 타격 효과가 쓰는 플립북(`styleTextures`, `styleArt.HIT_ART`: 메카 섬광은 `mecha/hitBurst`·`mecha/hitHold`, 클럽 링 · 크리스털 파편 · 네온 아크 · 피아노 음표는 `club/…` · `gem/…` · `neon/…` · `piano/…`, 플래시 · 플레어 · 거품 · LED 그리드는 `flash/…` · `flare/…` · `bubbles/…` · `grid/…`)을 텍스처 칸에 넣는다. 플립북은 판정선이 그림 위쪽에 있어(`anchorY`) 판정선 아래로 퍼지고, 불러오지 못하면 코드로 그린다(세트의 효과는 플래시로). 플레이 캔버스의 `data-art`가 그림으로 그린 부위를 적는다(`notes long side gear hit`).
  - 노트: 위에서 본 그림을 노트 모양(상자·납작·캡슐) 위로 내려 투영하고 알파가 윤곽이다. 부위를 늘 고르게 된 뒤로는 모든 스킨에 `style`이 있어 노트 메시는 판(`picture`)이고, 상자·납작·캡슐 메시는 쓰이지 않는다. 벽은 그림 가장자리에서 30% 안쪽 줄을 쓴다. 노트 크기(높이 0.2 · 깊이 0.7)는 그리는 노트와 같다. 그림 비율대로 깊이를 줄이면 8K 노트가 화면에서 그리는 노트의 60% 높이로 얇게 보였다. 사이드 레인은 키 레인보다 좁아 사이드 그림만 2:1이다.
  - 롱노트 몸통: 실제 꼬리 위치에 고정한 UV로 텍스처가 노트와 함께 흐른다(누르는 동안에도). 몸통 메시마다 UV를 갖는다.
  - 바닥: 트랙 색(가까운 쪽 → 먼 쪽)에 타일을 곱하고, 타일 평균을 1로 되돌리는 이득(sRGB `gain`, 선형으로 ^2.2)을 정점 색에 곱한다.
  - 판정선·키 빔·타격 이펙트·롱노트 불꽃은 순흑 바탕 빛이라 가산 합성한다. FEVER 색 바꾸기는 그대로다. 레일 텍스처는 읽기만 하고 그리지 않는다(트랙 테두리는 기어의 것).
  - 타격 이펙트(`hitEffect: 'sprite'`)는 4×4 플립북을 스프라이트 풀에서 칸을 바꿔 한 번 재생하고 마지막 30%를 흐린다. 시트 복사본은 이미지를 공유하고 UV만 다르다. 롱노트 불꽃은 레인마다 다른 칸에서 반복하고 아래쪽이 판정선에 닿는다. "번쩍임 줄이기"는 밝기·크기를 매니페스트의 `effects` 비율로 줄인다. 타격 효과를 부위로 고르게 된 뒤로 `flipbook`은 고를 수 없어 이 경로는 지금 쓰이지 않는다.
  - 텍스처는 밉맵 한 단계만 읽는다(`LinearMipmapNearestFilter`). SwiftShader에서 3선형보다 읽기가 절반이라 8K 프레임 시간이 18.8–20.4 → 17.6–18.2ms로 줄었다(아래 "그 뒤").
- **배경**(`ui/PlayBackground.ts`): 트랙 캔버스 뒤 DOM 층. 흐린 앨범아트, 사용자 영상(BGA, 소리 없음, 곡 시간 − 오프셋에 맞춰 재생하고 0.12초 넘게 어긋나면 최대 0.5초에 한 번 다시 맞춤. 유튜브 링크는 `ui/youtubeBga.ts`가 유튜브 플레이어를 음소거로 띄워 같은 방식으로 맞추되, 플레이어의 시간 보고가 거칠어 0.25초 넘게 어긋나면 1.5초에 한 번까지만 다시 맞춤), 밝기 조절용 어두운 막. 판정·클럭과는 무관하다. 음악에 반응하는 `AnalyserNode` 스펙트럼(`canvas.bg-visualizer`, 30fps, 로그 간격 48밴드 좌우 대칭)은 코드에 남아 있지만 설정 `visualizer`가 늘 꺼져 있어 그리지 않는다.

### 데이터 폴더

```
data/
  library.sqlite3          곡·채보·기록 메타데이터(곡의 `cover_at`, 채보의 `source_level`: BMS #PLAYLEVEL·bmson level 그대로)
  songs/<songId>/
    original.<ext>         업로드 원본
    audio.flac             표준 오디오
    cover.<ext>            앨범아트(있으면)
    analysis.json          AnalysisResult
    stems/<name>.flac      분리한 스템(16bit FLAC 4개, 합 = 표준 오디오) + stems.json(분리 방법)
    bga.<ext>              배경 영상(있으면)
    keysounds/sprite.flac  가져온 BMS·bmson의 키음을 이어 붙인 파일 + sprite.json(각 소리의 위치, 게인)
  charts/<chartId>.json    채보(생성·편집·가져옴; charts 테이블의 kind)
  replays/<scoreId>.json   기록마다 그 플레이의 리플레이
```

`songId`는 원본 파일의 SHA-256 앞 16자리다. 같은 파일을 다시 올리면 같은 곡으로 처리한다. 이전 버전의 `library.sqlite3`는 서버가 시작할 때 빠진 열을 추가해(`ALTER TABLE … ADD COLUMN`) 그대로 쓴다.

### 분석 백엔드 (`analysis/backends/`)

- 종류는 stems · beats · pitch · structure 네 가지이고, 어댑터마다 라이브러리를 **처음 쓸 때만** 불러온다. 설치 여부는 `importlib.util.find_spec`으로만 확인하므로 PyTorch가 설치되어 있어도 서버 시작이 느려지지 않는다.
- 옵션은 `config/analysis.json`의 `ml`(모델 이름·장치·shifts 등). `ml.enabled=false` 또는 `GRG_ML=0`이면 모두 끈다.
- 분석기는 단계마다 ML 결과가 있으면 쓰고, 예외가 나면 그 단계만 기본 분석으로 돌린 뒤 `analyzer.errors[단계]`에 남긴다. 실제로 쓴 백엔드는 `analyzer.backends`(예: `{"stems": "demucs-4.1.0", "beats": "beat_this-1.1.0", "pitch": "core", "structure": "core"}`)에 기록한다.
- ML 결과는 기본 분석의 입력으로 들어간다: beat_this 박 간격은 템포 추정의 BPM 힌트와 박자·첫 다운비트(그리드는 여전히 전곡 온셋 정렬로 정밀 맞춤), basic-pitch 노트는 가까운 온셋의 음높이, allin1 구간은 마디에 스냅해 구조로, Demucs 스템은 온셋 태깅·구간 주도 악기·키음 스템으로 쓴다.
- 곡 목록의 `outdated`는 저장된 분석의 분석기 버전이 다르거나, 지금 쓸 수 있는 백엔드가 분석 때 쓴 것과 다르면 true다. 클라이언트는 이때 "다시 분석" 버튼을 보인다.

### Phase 1 — MVP

1. 서버: 업로드·표준 FLAC·태그/커버, SQLite 라이브러리, 백그라운드 분석 작업, API
2. 기본 분석: STFT·멜 스펙트럼, 멀티밴드 스펙트럴 플럭스 온셋, HPSS, 템포 추정과 고정 BPM 그리드 정밀 맞춤(드리프트 검사), 다운비트, 지속음, 구간·에너지·반복 묶기, 음높이 윤곽
3. 생성기: 양자화, 후보 점수화, 밀도 제어, 손가락 모델 기반 레인 배치(빔 서치), 롱노트, 스크래치, 린터, 레벨 산정 루프, 결정적 시드

5. 개발 도구: 분석 결과 시각화, 생성 CLI
6. 검증: pytest(그리드 오차 ≤ 10ms, 결정성, 린터, 난이도 단조성, 성능), Vitest, Playwright E2E(업로드 → 생성 → 오토 플레이 → 결과)
