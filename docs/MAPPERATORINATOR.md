# Mapperatorinator: 채보 생성

채보는 Mapperatorinator(OliBomby/Mapperatorinator, osu!mania용 AI)가 사용자 PC의 NVIDIA GPU에서 만든다. 다른 생성기는 없다.

- 2026-11-09 `claude/mapperatorinator` 브랜치에서 시작했다(요청: "generative rhythm에서 브랜치 따로 파서 이 mapperatorinator를 적용한 버전으로 새로 하나 빌드해줄래?"). 모든 키 모드를 Mapperatorinator로 만들고, 7K+1S는 8K로 만들어 맨 왼쪽 열을 스크래치로 쓴다.
- 2026-11-11 `claude/mapper-only` 브랜치에서 예전의 규칙 기반 생성기를 지웠다(사용자 결정). 지운 것과 남은 일은 이 문서 끝의 "mapper 전용 정리"에 있다.

## 무엇이 바뀌었나

- **채보 생성**
  - 곡을 열면 그 채보를 Mapperatorinator(OliBomby/Mapperatorinator, 코드 MIT)가 만든다. 가중치는 `OliBomby/Mapperatorinator-v32`의 mania 전용 `gamemode=3`(MIT)이다.
  - 분석기는 키음 스템(스템 분리 · 온셋)과 구간 표시에 쓰인다. 박자(BPM · 마디선)는 분석기가 아니라 모델의 것을 쓴다.
- **실행 환경**
  - CUDA용 PyTorch는 2GB가 넘어 NSIS 설치 파일에 들어가지 않는다.
  - 그래서 앱이 처음 쓸 때 사용자 폴더(`%LOCALAPPDATA%\Generative Rhythm\mapper`)에 따로 Python 환경을 만든다. 들어가는 것은 다음과 같다.
    - uv(PyPI 휠, sha256 확인)
    - Python 3.11
    - PyTorch 2.10 + CUDA 12.6
    - Mapperatorinator의 추론 패키지(requirements.txt와 같은 버전)
    - 소스(설치 파일에 들어 있는 고정 커밋 5884d1b)
    - 가중치(Hugging Face, 약 0.9GB)
  - 모두 합쳐 약 4GB를 내려받는다.
  - **설정 → 고급 → AI 채보 (Mapperatorinator)**의 **설치** 버튼으로 시작하고, 진행률이 그 자리에 나온다.
- **채보를 만드는 방식** (`server/rhythm_server/mapper/`)
  1. 서버가 곡의 오디오(WAV)를 넘긴다.
  2. 박자는 모델이 찾는다. 곡의 첫 채보는 타이밍 없이 요청해서, 모델이 곡 전체를 한 번 지나며 박자를 찾고(TIMING 패스) 이어서 노트를 만든다. 그 박자를 곡에 남겨 두고(`songs/<곡>/mapper_timing.json`, 모델별), 그 곡의 다른 채보를 만들 때는 타이밍만 있는 `.osu`로 넘긴다(`in_context=[TIMING]`). 그래서 티어끼리 BPM과 마디선이 같고, 두 번째 채보부터는 박자 패스를 건너뛰어 빠르다. 곡 목록의 BPM은 이 박자에서 나온다(가장 오래 이어진 템포). 첫 채보가 생기기 전에는 비어 있다.
  3. 별점, 키 수, 시드를 정해 따로 뜬 작업 프로세스(`worker.py`, 모델을 띄워 둔 채 한 번에 하나씩)에 요청한다.
  4. 돌아온 osu!mania 채보를 앱 채보로 바꾼다.
  5. 변환된 채보에 앱의 레벨 추정, 패턴 요약, 구간, 카메라 연출을 붙인다. 분석한 구간은 시각만 가져와 채보의 박에 다시 놓는다(분석기의 박 번호는 모델의 박자와 다르다). 노트마다 가장 가까운 온셋의 스템을 달아 스템 키음 모드도 그대로 동작한다.
- **키 모드**

  | 앱 | Mapperatorinator | 비고 |
  |---|---|---|
  | 4K · 5K · 6K · 8K | 같은 키 수 | |
  | 7K+1S | 8K | 0번 열이 스크래치 |
  | 4K+FX · 6K+FX | 4K · 6K | FX 레인은 비어 있음 |

- **난이도**
  - 티어마다 레벨 범위의 가운데(목표 레벨을 고르면 그 레벨)를 osu! 별점으로 바꿔 요청한다.

    | 앱 레벨 | 1 | 4 | 7 | 10 | 13 | 15 | 17 | 20 |
    |---|---|---|---|---|---|---|---|---|
    | 별점 | 1.0 | 1.8 | 2.6 | 3.4 | 4.3 | 5.0 | 5.7 | 7.0 |

    중간 레벨은 직선으로 잇는다(`config/mapper.json` `starsForLevel`).
  - 화면에 보이는 레벨은 만들어진 노트를 앱이 직접 잰 값이다.
  - 이 대응은 아직 맞추지 않은 첫 값이다. 집에서 플레이한 채보의 실제 레벨과 견줘 고칠 곳이다(설정의 난이도 배율로 먼저 맞춰 볼 수 있다).
- **곡 선택 화면**
  - 채보는 Enter를 눌렀을 때 만들어진다(GPU에서 곡당 1–3분 예상). 커서를 티어에 올려 두는 것만으로는 만들지 않는다. 그렇게 하면 지나간 티어마다 GPU 작업이 줄을 선다.
  - 아직 없는 채보에 Enter를 누르면 서버에 요청만 하고 바로 돌아온다. 화면은 막히지 않는다. 그동안 다른 곡이나 이미 만들어진 채보를 플레이할 수 있고, 아래 상태 줄에 무엇을 만들고 있는지 나온다. 다 되면 상태 줄에 "준비되었습니다"가 나오고 티어 칸이 레벨로 바뀐다. 몇 분이 지난 뒤라 저절로 시작하지는 않는다. Enter를 다시 누르면 플레이한다. F5(새 패턴)도 같다.
  - 한 티어를 요청하면 그 채보를 먼저 만들고, 이어서 같은 키 모드의 나머지 티어를 뒤에서 하나씩 만든다. 뒤에서 기다리던 티어에 Enter를 누르면 그 티어가 맨 앞으로 온다. 이미 만들고 있는 채보는 중간에 멈추지 않는다.
  - "만드는 중" 표시는 그 채보 하나에만 붙는다. 커서를 옮겨도 다른 티어나 다른 곡이 "만드는 중"으로 바뀌지 않는다(첫 빌드의 버그였다).
  - 티어 칸에는 상태가 나온다.
    - "AI · 만드는 중": 지금 GPU가 만들고 있다.
    - "AI · 대기 중": 차례를 기다린다.
    - "AI · 열면 만듦": 아직 줄에 없다.
  - 다 만들어지면 칸이 실제 레벨과 노트 수로 바뀐다. 곡 선택 화면이 5초마다 다시 묻는다.
  - 한 번 만든 채보는 저장되어 다시 열면 바로 나온다.
  - 뒤에서 만드는 동안 플레이하면 게임 화면과 GPU를 나눠 써서 끊김이 있을 수 있다.
- **설정** (설정 → 고급 → AI 채보 (Mapperatorinator))
  - 설정값은 실행 환경 폴더의 `settings.json`에 남는다. 앱을 새 빌드로 다시 설치해도 그대로다. 설치 파일 안의 `config/mapper.json`은 기본값이다.
  - 모델, 롱노트 비율, 다양성, 난이도 배율은 채보 ID에 들어간다. 바꾸면 이제부터 만드는 채보가 달라지고, 이미 만든 채보는 저장된 채 남는다. 곡 선택 화면의 티어 정보도 새로 받는다.
  - 모델이나 정밀도를 바꾸면 작업 프로세스가 먼저 올라 있던 모델을 GPU에서 내린다.

  | 항목 | 값 | 기본 |
  |---|---|---|
  | 모델 | v32 · v32-mini(작고 빠름, 처음 쓸 때 약 0.2GB 받음) | v32 |
  | 연산 정밀도 | 자동 · fp16 · fp32. 자동은 bf16을 지원하면 bf16, 아니면 fp32이고, RTX 20xx는 fp32다(설정 화면이 이 PC의 자동값을 보여 준다). fp16은 RTX 20xx에서 몇 배 빠르지만 인코더는 fp32로 돈다(아래 "fp16") | 자동 |
  | 난이도 배율 | ×0.5–×2.0. 티어 레벨을 바꾼 별점(`starsForLevel`)에 곱한다 | ×1.00 |
  | 롱노트 비율 | 자동 · 0–100% | 자동(모델이 정함) |
  | 다양성(temperature) | 자동 · 0.30–1.50 | 자동(v32는 0.9) |
  | 히트사운드 생성 | 켬 · 끔. 끄면 노트 하나의 토큰 5개 가운데 히트사운드 · 볼륨 2개를 만들지 않아 디코딩이 그만큼 짧다. 히트사운드는 카메라 연출의 강세로 쓴다(아래 "카메라") | 켬 |
  | 이전 문맥 | 30–80%. 16.4초 창의 앞부분을 이미 만든 노트로 채우는 몫 | 50% |
  | 앞 미리보기 | 0–60%. 창의 뒷부분을 노트 없이 보여 주는 몫. 둘을 합쳐 90%까지이고, 나머지만큼 창이 나아간다(기본값이면 1.6초씩, 4분 곡에 창 약 146개) | 40% |
  | 병렬 생성 | 켬 · 끔. 창을 독립적으로 8개씩 묶어 만든다. 빠르지만 창 사이 문맥이 없다 | 끔 |

  - 예전 빌드의 "AI 채보 쓰기"와 "앱의 박자 쓰기" 설정은 없어졌다. 서버는 그 값을 받아도 무시하고, 물으면 늘 켬 · 끔(모델 박자)으로 답한다(화면이 정리되기 전까지 깨지지 않게).
  - 스크롤 속도(SV) 생성은 항상 건너뛴다. 모델의 출력 순서는 타이밍 → 노트 → SV인데 노트만 요청하면 SV 단계가 빠진다. 곡의 첫 채보는 타이밍과 노트 두 단계, 그 뒤 채보는 노트 한 단계만 돈다. 앱은 SV를 쓰지 않으니 채보에는 영향이 없다.

- **GPU가 없거나 실패할 때**
  - 다른 생성기가 없으므로, 채보를 만들 수 없으면 이유를 보여 주고 다시 시도하게 한다. 곡 선택 화면에서 Enter를 다시 누르면 다시 요청한다.
  - 실행 환경을 아직 설치하지 않았으면 "설정에서 설치해 주세요", 설치 중이면 "설치가 끝난 뒤 다시", NVIDIA GPU가 없는 PC(회사 PC)에서는 "NVIDIA GPU가 없어 AI 채보를 만들 수 없습니다"가 나온다(서버 응답 503).
  - 생성이 실패하면(메모리 부족 등) 작업 프로세스의 오류와 "다시 시도해 주세요"가 나온다(502). 설정 화면에도 마지막 실패가 남는다.
  - 티어 칸의 "AI · 열면 만듦"(목표 레벨)은 실행 환경이 없어도 나온다.
  - NVIDIA GPU가 없는 PC에서 CPU로 만들게 할지(v32-mini)는 아직 정하지 않았다. 지금은 만들지 않는다. 서버 쪽 길은 있다(`GRG_MAPPER_ALLOW_CPU=1`, 빌드의 CPU 시험이 쓴다).

## 빌드 결과물 받기

이 브랜치에 올릴 때마다 GitHub Actions의 **Desktop app (Windows)**가 설치 파일을 만든다. 실행 기록의 Artifacts에 30일간 남는다.

- 받을 것은 `GenerativeRhythm-Windows-Setup` 하나다. ML판 · 구조 분석판 설치 파일은 더 만들지 않는다.
- 예전 판을 이미 설치했다면 같은 앱이라 덮어쓴다. 라이브러리(곡·기록)는 그대로다.
- 빌드 작업은 러너의 CPU로 작은 모델(v32-mini)을 써서 실행 환경 설치와 20초짜리 합성 곡 채보 하나를 끝까지 돌려 본다. 이 단계는 실패해도 빌드는 계속된다(PyPI · GitHub · Hugging Face에서 내려받는 단계라서). 기록은 `windows-smoke-test` 아티팩트의 `setup.log` · `worker.log`에 남는다.
- 이어서 설치한 앱을 띄워, 그 CPU 실행 환경으로 데모 곡의 채보를 앱 서버를 통해 만든다(박자 패스 포함). 실행 환경이 없으면 채보 요청이 이유와 함께 거절되는지만 확인한다.

## 알려진 한계

- **실제 실행은 아직 CPU 시험 한 번뿐이다.**
  - 클라우드 세션에서는 Mapperatorinator를 돌리지 못한다. 외부 코드를 내려받아 실행하는 것이 안전 장치에 막혔고 GPU도 없다. 그래서 코드를 읽어 연결했고, 서버 흐름은 가짜 작업 프로세스로 시험한다(`server/tests/test_mapper.py`, `server/tests/fakes.py`).
  - 처음 실제로 돈 것은 Windows 빌드(실행 293, 기본판 작업)의 CPU 단계다. GPU가 없는 GitHub 러너에서 v32-mini로 돌렸다.

    | 단계 | 결과 |
    |---|---|
    | 실행 환경 설치(uv · Python 3.11.15 · PyTorch 2.10.0+cpu · 패키지 · 소스 · 가중치) | 35.5초 |
    | 20초 합성 곡, 7K+1S HARD(목표 레벨 6 → 별점 2.33) | 노트 64개, 앱이 잰 레벨 1 |
    | 생성 시간 | Mapperatorinator 9.9초, 변환까지 16.3초(CPU, fp32) |

  - 한 번 돌았다는 것만 확인했다. 요청 → `.osu` → 앱 채보까지 이어진다. 품질은 아직 모른다. 짧은 합성 곡이라 레벨 1은 별점 대응을 판단할 근거가 못 된다.
  - 집 PC(NVIDIA, v32)에서 실제 곡으로 확인하는 것이 다음이다.
- **RTX 2060**
  - bf16을 지원하지 않아 자동은 fp32로 돈다(Mapperatorinator 자체 판단).
  - 6GB판이면 긴 곡에서 메모리가 빠듯할 수 있다. 실패하면 오류가 나오고 다시 시도할 수 있다.
  - 집 PC에서 fp16이 fp32보다 눈에 띄게 빨랐다(초 단위는 아직 재지 않았다. 채보 정보의 "AI 생성" 줄이 걸린 초를 보여 준다).
- **fp16**
  - 집 PC(RTX 2060, fp16)에서 곡의 거의 마지막 구간에서 채보가 망가졌다: 박자가 이상해 보였고, 롱노트를 누르는데 콤보가 2개쯤만 올랐고, 노트 배치도 이상했다. fp32는 정상이었다.
  - 그때 채보의 BPM은 모델의 박자 패스(TIMING)에서 나왔고, 그 패스가 fp16에서 마지막 구간에 망가진 것이다. 롱노트 틱은 채보의 BPM을 따르므로, BPM이 틀리면 콤보도 거의 오르지 않는다.
  - **지금은 늘 모델의 박자를 쓴다.** 그래서 fp16에서 곡의 첫 채보가 이렇게 망가지면 그 박자가 곡에 남아 다른 티어에도 간다. 아래 보완(인코더 fp32)이 이를 막는지는 집 PC에서 확인해야 한다. 망가진 박자를 버리려면 곡 폴더의 `mapper_timing.json`을 지우고 채보를 다시 만든다(화면에서 하는 방법은 아직 없다).
  - 원인으로 보는 것: Mapperatorinator는 fp16을 고르면 모델 전체를 fp16으로 바꾼다. 인코더 입력은 피크 정규화한 음원의 파워 멜 스펙트로그램(로그 없음)이라 큰 소리 구간에서 값이 수천이고, 모델은 bf16(범위가 fp32와 같다)으로 학습됐다. fp16은 65504에서 끝나므로 인코더 앞단(멜 투영, 합성곱)이 큰 소리 구간에서 넘칠 수 있다(inf → HF Whisper 인코더 층의 clamp 또는 NaN). 그 구간의 창들은 엉뚱한 노트가 된다. 곡의 마지막 절정이 가장 큰 소리라 "마지막 구간"과 맞는다. 디코더에서 넘칠 가능성도 남아 있다.
  - 보완: `worker.py`의 `encoder_fp32`. fp16 모델의 인코더 쪽(멜 스펙트로그램 → 조건 임베딩 → 인코더)을 fp32 복사본으로 돌리고, 나온 은닉 상태만 fp16으로 바꿔 디코더에 준다. 인코더는 디코딩 전에 창들을 한 번에 지나는 한 패스(몇 초)이고 시간은 거의 디코더가 쓰므로 fp16의 속도는 거의 그대로다. 두 경로를 모두 덮는다: 순차 생성의 `precompute_encoder_outputs`(모델 대신 fp32 대역을 읽게 함)와 병렬 모드의 `model.get_encoder()`(fp32 부품으로 만든 인코더로 바꿈). GPU 메모리를 인코더 한 벌(fp32)만큼 더 쓴다.
  - 채보 정보의 "AI 생성" 줄에 `fp16(인코더 fp32)`로 표시된다. 이전 빌드의 fp16 채보(`fp16`만 표시)와 구분된다.
  - 이 보완은 클라우드에서 시험하지 못했다(여기서는 Mapperatorinator를 돌릴 수 없다). 집 PC에서 같은 곡을 fp16으로 다시 만들어 마지막 구간을 확인해야 한다. 그래도 망가지면 디코더 쪽 넘침이라 fp16은 쓸 수 없고 fp32만 남는다.
  - fp16으로 이미 만든 채보는 저장된 채 남아 있다. 다시 만들려면 그 채보에서 F5(새 패턴).
- **NVIDIA 드라이버**
  - CUDA 12.6용 PyTorch라 드라이버 560 이상이 필요하다.
  - 설치 마지막의 확인 단계에서 GPU를 못 쓰면 "드라이버를 최신으로" 안내와 함께 실패한다.
- **학습 데이터**
  - 학습 데이터는 project-riz/osu-beatmaps다. osu! 랭크·러브드 비트맵 213,068개, 곡 46,386개로, 74개 묶음 가운데 0–71번이 학습용이다.
  - 학습 설정에 키 수로 거르는 조건은 없다.
  - 74개 묶음의 채보 정보를 모두 읽어 mania 채보를 키 수(CircleSize)별로 셌다. 전체 수는 데이터셋 설명서와 같다. 학습용 mania 채보는 26,572개다.

    | 4K | 18,971 | 71.4% | 6,848 | 4K · 4K+FX |
    | 7K | 4,889 | 18.4% | 1,761 | (쓰지 않음) |
    | 6K | 896 | 3.4% | 445 | 6K · 6K+FX |

  - 7K는 4,889개로 8K의 17배다. 7K+1S를 "7K로 만들고 스크래치는 규칙으로 붙이기"로 바꾸면 건반 쪽 패턴은 더 많은 데이터를 쓰게 된다. 아직 바꾸지 않았다.
- **osu! 채보 습관(집 PC에서 본 것)**
  - 롱노트가 많다.
    - v32는 롱노트 비율을 조건으로 학습했다(`add_hold_note_ratio_token: true`). 설정의 "롱노트 비율"이 그 값을 모델에 넘긴다(`hold_note_ratio`). 10% 단위로 반올림되고, 0%는 "롱노트가 없는 채보" 조건이다.
    - 사람 BMS 7키 채보의 롱노트 몫은 레벨 7–15에서 1–3%다(PATTERN_DESIGN 71장). 0–5%가 가깝다.
    - 비율만 정한다. 롱노트를 어디에 둘지는 모델이 정한다.
  - 같은 소리의 반복(드럼 롤, 같은 음 반복)을 연타 대신 계단·아르페지오(1234, 2345, 4565)로 만든다. osu!mania에서 흔한 롤 패턴이다.
    - Mapperatorinator에는 이것만 고르는 설정이 없다.
    - 스타일 태그(`descriptors`): v32는 osu! 사용자 태그 122개를 조건으로 학습했다. 연타 쪽 태그와 그 태그가 붙은 학습 채보 수(모든 모드 합계, 태그가 붙은 채보는 24,975개)는 아래와 같다. 태그는 채보 전체의 스타일을 바꾸므로 반복 구간이 아닌 곳에도 연타가 생긴다. 키 수별로는 세지 않았다. mania 학습 채보의 71%가 4K라 대부분 4K로 본다.

      | 태그 | 학습 채보 |
      |---|---|
      | style/chordjack | 553 |
      | skillset/speedjack | 285 |
      | skillset/wristjack | 135 |
      | style/longjack | 94 |

    - 피할 태그(`negative_descriptors`)는 classifier-free guidance(`cfg_scale` > 1)로만 작동한다. 디코더가 토큰마다 조건 있는 쪽과 없는 쪽을 함께 돌려 느려진다.
    - `mania_column_temperature`(기본 0.8)를 낮추면 열 고르기가 보수적이 된다. 반복 구간만 겨냥하지는 않는다.
    - 겨냥하는 방법은 앱 쪽 후처리다(만들지 않았다). 같은 소리가 같은 간격으로 4타 이상 이어지는 줄기의 레인만 바꾸는 것인데, 소리 묶음과 음높이는 앱의 온셋 · 음높이 분석에서 나온다. 그 분석을 정리하기로 했으므로(아래 "mapper 전용 정리") 이 길은 접는다.
- **앱 규칙이 적용되지 않는 부분**
  - 앱의 플레이 규칙 검사(최소 연타 간격, 동시 노트 수 등)를 적용하지 않는다. 구조 검사(겹침, 길이 0 롱노트)만 한다.
  - 레벨이 티어 범위를 벗어날 수 있다.
- **처음 쓸 때**
  - 설치에 인터넷과 시간이 든다(약 4GB). 받는 곳은 PyPI, download.pytorch.org, GitHub(Python), Hugging Face다.
  - 실행 환경을 지우려면 앱을 끈 뒤 `%LOCALAPPDATA%\Generative Rhythm\mapper` 폴더를 지운다.
- **라이선스**
  - Mapperatorinator의 코드와 가중치는 MIT다. 함께 받는 slider(OliBomby 포크)는 원 저장소의 라이선스를 따른다.
  - Mapperatorinator README는 "AI 사용을 밝힐 것"을 당부한다.

## 카메라: Mapperatorinator 결과만으로 움직일 수 있나 (2026-11-11 확인)

요청: "카메라 웍도 mapper 분석결과에 따라 다이나믹하고 음악에 맞춘 역동적인 움직임이 가능할지 확인", "현재 앱의 곡 구조분석은 사용하지 않고 mapperatorinator 분석 결과만으로 가능한지 먼저 확인해줘".

**결론: 가능하다.** 앱의 곡 구조 분석 없이, 채보의 노트와 히트사운드만으로 지금과 같은 종류의 연출(줌 펄스 · 유지되는 줌 · 기울기)을 만들 수 있다. 시험판이 이 브랜치에 들어 있다(`server/rhythm_server/chart/camera_notes.py`, `config/mapper.json`의 `cameraFrom: "notes"`). 클라이언트의 카메라 재생(`cameraFx.ts`)은 바꾸지 않았다. 신호의 형식이 그대로라서다.

- **히트사운드 생성은 켜 둔다**(기본값). 끄면 생성이 빨라지지만 박 펄스의 근거가 없어져 동시치기(화음) 크기로 대신한다.
- v32-mini의 박자는 템포가 일정한 곡에서도 빨간 선이 여러 개로 흔들린다(120 BPM 곡에 119.7–123). 집 PC의 v32는 BPM과 마디선이 잘 나왔다고 했으므로 모델 차이로 본다. 시험판은 구간을 마디 단위로 자르므로 마디선이 틀리면 연출의 자리도 그만큼 어긋난다.

### 시험판이 하는 일

구간 기반 카메라(`effects.py`)에 넘기던 "구간 · 온셋 · 롤"을 채보에서 만든다. 연출을 만드는 코드는 같다.

1. 마디마다 박당 노트 수를 세고, 곡의 바쁜 마디(상위 10%)를 1로 둔다.
2. 다음 두 마디의 평균이 앞 두 마디와 0.2 이상 달라지는 마디에서 구간을 자른다. 더 바쁜 구간은 그 수준에 이른 마디부터 시작한다.
3. 구간의 세기는 곡 안에서 가장 한산한 구간이 0, 가장 바쁜 구간이 1이다. 0.7 이상이면 바쁜 구간(기울기 · 박 펄스), 0.25 이하면 조용한 구간(시야 넓힘)이다.
4. 바쁜 구간 앞에서 마디가 두 번 이상 연달아 차오르면 빌드업이다(마디마다 줌을 조이고, 다음 구간이 시작할 때 놓으며 펄스).
5. 박 펄스는 clap · finish가 붙은 박 위의 노트에 준다(히트사운드가 없으면 동시치기가 큰 노트).

두 곡에서 나온 신호 수: 줌 펄스 128 · 89, 기울기 11 · 3, 유지 줌 3 · 2.

### 지금 카메라와 다른 점

- 구간 이름(후렴 · 드롭 · 브레이크다운)을 모른다. "바쁘다 · 한산하다"만 안다. 조용하지만 중요한 구간(잔잔한 후렴)은 바쁜 구간으로 잡히지 않는다.
- 티어마다 노트가 다르므로 카메라도 티어마다 조금 다르다. 낮은 티어는 밀도 차이가 작아 연출이 줄 수 있다.
- 멜로디가 오르내리는 방향으로 기우는 것은 없어진다(음높이 분석이 없다). 노트가 한 손에 몰리지 않으면 기울기 방향을 번갈아 준다.
- 곡 구조 분석(ML판의 allin1 포함)과 무관해져, 분석 없이도 같은 연출이 나온다.

### 고를 것

- **노트 기반으로 간다(추천)**: 곡 구조 분석을 지울 수 있다. 집에서 시험판 빌드로 몇 곡을 만들어 연출이 음악에 맞는지 본 뒤 정한다. 이미 만든 채보의 카메라는 그대로이므로 F5(새 패턴)나 다른 티어로 새로 만들어야 보인다.
- 구간 기반을 남긴다: `config/mapper.json`의 `cameraFrom`을 `"structure"`로 두면 예전과 같다. 곡 구조 분석도 남는다.

### 남은 일

- **분석 모듈 정리.** 박자 분석(`analysis/tempo.py` · `meter.py`, beat_this)은 쓰임이 없어졌지만 아직 지우지 않았다. 곡 구조 분석이 그 박 위에서 돌기 때문에 둘을 함께 지워야 한다. 곡 구조는 위 카메라 결정이 난 뒤에 지운다. 음높이 분석(`analysis/pitch.py`, basic-pitch)도 온셋의 "새 소리인지" 판단에 얽혀 있어, 키음(스템 분리 · 온셋 분석)을 남길지 정해진 뒤에 한 번에 정리한다.
- 구간 표시 · 구간 편집 · 미리듣기 시작 위치는 아직 곡 구조 분석에서 나온다. 곡 구조를 지우면 대신할 것을 정해야 한다(미리듣기는 세션 4).
- `config/difficulty.json` · `instruments.json`에 생성기만 읽던 값이 남아 있다. 클라이언트가 같은 파일을 읽으므로 화면 정리(세션 1) 뒤에 줄인다.
- `docs/PATTERN_DESIGN.md`는 생성기 설계 기록이지만 남은 분석 코드가 그 장 번호를 가리켜서 분석 정리 때 함께 지운다. `.github/workflows/allin1-windows-experiment.yml`도 그때 지운다.
- 화면(세션 1)이 고칠 곳: 설정의 "AI 채보 쓰기" · "앱의 박자 쓰기" 항목, 마지막 실패 문구("그 채보는 기존 생성기로 만들었습니다"), 곡 정보의 BPM ×2 · ÷2 · 자동으로 버튼(앱의 박자 분석에만 작용한다), 플레이 옵션의 생성 옵션. `chartCache.ts`는 서버의 generator 표기에 `+mapper-`가 있는지로 AI 채보 모드를 판단하므로 서버가 그 표기를 유지한다.
- NVIDIA GPU가 없는 PC에서 CPU(v32-mini)로 만들게 할지 정하지 않았다. CPU에서 3–4분 곡의 첫 채보에 약 5분이 걸렸다(GitHub 러너, 박자 패스 포함).
- fp16에서 박자 패스가 곡 끝에서 망가지던 문제의 보완(인코더 fp32)은 집 PC에서 아직 확인하지 못했다. 이제 늘 모델 박자를 쓰므로 fp16을 쓴다면 먼저 확인해야 한다.
- 망가진 곡 박자를 화면에서 버리는 방법이 없다(`mapper_timing.json`을 직접 지워야 한다).
